# MTFL / `kwrb` — формат игровой справки (окно KeyWord) Super Robot Wars V

Описание получено реверс-инжинирингом собственной копии игры для фанатского
перевода. Файлы игры не модифицируются — патч собирается в отдельный CPK.

* Исходник (EN): `CommonData/MtData/EN/MtV_all_keyword_def.cpk` → `00000000.dat`
* Исходник (JP): `CommonData/MtData/MtV_all_keyword_def.cpk` → `00000000.dat`
* Инструмент: `_tools/ru_mtfl.py`

Чтобы получить `.dat`:

```
python _tools/cpk_extract.py   <file.cpk> <dir>
python _tools/srwv_decrypt.py  <dir>      <dir_dec>     # Blowfish
```

| | EN | JP |
|---|---|---|
| размер `.dat` | 112 776 | 125 870 |
| статей | 147 | 147 |
| строк в пуле | 348 | 349 |

---

## 1. Общая схема

```
+0x00  файловый заголовок (32 байта)
+0x20  секция 'kwrb'            ← единственная секция верхнего уровня
         +0x30  секция 'lkke'   ← таблица статей (147 × 40 байт)
         +…     секция 'jstr'   ← обфусцированный пул строк
       хвост 'ENDoMTFLsrc>' + путь сборщика (НЕ обфусцирован)
```

## 2. Файловый заголовок (0x20 байт)

| смещение | тип | EN | описание |
|---|---|---|---|
| 0x00 | char[8] | `MTFLz2_2` | магия |
| 0x08 | u32 | `0x20` | размер заголовка |
| 0x0C | char[4] | `0.94` | версия |
| 0x10 | u32 | `112625` | размер контента (== `kwrb.total`) |
| 0x14 | u8[12] | нули | резерв |

`0x20 + content_size` = начало хвоста. Хвост — 119 байт:
`ENDoMTFL` + `src>` + путь `c:/convert/.../mtv_all_keyword_def.h` (ASCII,
без завершающего нуля, без обфускации). Переносится в сборку как есть.

## 3. Заголовок секции (16 байт, иногда больше)

| смещение | тип | описание |
|---|---|---|
| +0 | char[4] | тег |
| +4 | u32 | `total` — полный размер секции **вместе с заголовком** |
| +8 | u32 | `hdr` — размер заголовка |
| +12 | u32 | `payload` — размер данных (`total == hdr + payload`) |
| +16 | … | дополнительные поля, если `hdr > 16` |

Секции идут вплотную, без выравнивания. Вложенность: `kwrb` содержит
`lkke`, затем `jstr`.

* `kwrb`: `hdr = 16`, доп. полей нет.
* `lkke`: `hdr = 20`, доп. поле `u32 entry_count` на `+16` (= 147).
  `payload == entry_count * 40`.
* `jstr`: `hdr = 16`, `payload` — пул строк.

## 4. Секция `lkke` — таблица статей

147 записей по 40 байт (10 × u32):

| # | поле | смысл |
|---|---|---|
| 0 | `term_off` | смещение термина в пуле |
| 1 | `term_len` | **длина в кодовых точках Unicode**, не в байтах |
| 2 | `series_off` | смещение названия сериала-первоисточника |
| 3 | `series_len` | длина |
| 4 | `desc_off` | смещение описания (до прохождения) |
| 5 | `desc_len` | длина |
| 6 | `desc2_off` | смещение описания после прохождения сценария |
| 7 | `desc2_len` | длина |
| 8 | u32 | всегда `0xFFFFFFFF` (не используется) |
| 9 | `id` | стабильный id ключевого слова, уникальный, 0…146 |

Важно: **поля длины считают кодовые точки UTF-8, а не байты.** Для чисто
латинского текста это совпадает, но `–` (U+2013), `　` (U+3000) и кириллица
дают расхождение. Проверено на всех 588 строках обоих файлов: `len` всегда
равен `len(str)` в Python.

Порядок записей (idx) одинаков в EN и JP, и `id` по каждому idx совпадает,
т.е. idx — «слот» статьи, общий для всех локализаций.

### Поле `desc2` (текст после прохождения)

Строка `desc2` может быть:

| вид | кол-во (EN/JP) | смысл |
|---|---|---|
| ровно `<srw-tag=before-clear-text-here>` | 111 | после прохождения показывается то же, что и до |
| `<srw-tag=before-clear-text-here>` + хвост | 19 | к `desc` дописывается хвост |
| произвольный текст без маркера | 12 | `desc` полностью заменяется |
| тот же слот пула, что и `desc` | 5 | то же самое, но через общий слот |

Маркер `<srw-tag=before-clear-text-here>` **никогда** не встречается внутри
`desc`, только в начале `desc2`.

## 5. Секция `jstr` — пул строк

Пул — обычный массив C-строк, разделённых `0x00`, **обфусцированный**.
У последней строки завершающего нуля нет (пул кончается её последним байтом).
Строки дедуплицированы: одинаковые тексты (названия сериалов, маркер
`<srw-tag=…>`) хранятся один раз, и несколько записей ссылаются на один слот.

В EN-файле 348 строк, из них 347 адресуются таблицей; слот 0
(`ダミー〕〔仝￠`, «dummy») ни на что не ссылается — заглушка, оставшаяся от
конвертера.

### 5.1. Обфускация — и ловушка с буквой `z`

```
enc(c) = dec(c) = c            если c == 0x00 или c == 0x7A
                  c ^ 0x7A     иначе
```

Это инволюция: одна и та же таблица шифрует и расшифровывает.

Почему именно так: разработчики хотели «зашумить» текст простым XOR 0x7A, но
при этом сохранить пул валидным массивом C-строк. Обычный XOR 0x7A перевёл бы
терминатор `0x00` в `0x7A`, а букву `z` (`0x7A`) — в `0x00`, т.е. разделители
и буквы `z` поменялись бы местами. Поэтому **обе эти кодовые позиции
исключены из преобразования**: `0x00` остаётся терминатором, а `z` остаётся
`z`.

Следствия:

* Байт `0x5A` (`Z`) в файле = пробел (`0x20 ^ 0x7A`) — отсюда «гребёнка» из
  `Z` в hex-дампе.
* Если применить наивный «XOR всего подряд», то `Gaizok` превратится в
  `Gai\0ok`, `realized` — в `reali\0ed`, а настоящий разделитель — в `z`.
  **Никакой эвристики для различения не нужно** — надо просто не трогать
  `0x00` и `0x7A`.
* Дополнительная страховка: границы строк всё равно заданы явно парами
  (offset, len) в `lkke`, парсер не полагается на поиск разделителей.

### 5.2. Кодировка текста

UTF-8. Переводы строк — `\n` (`0x0A` → `0x70` в обфусцированном виде).
Японский текст использует `　` (U+3000) для отступов.

Кириллица безопасна: UTF-8-байты `0xD0 0xBB` и т.п. все `>= 0x80`, ни один не
равен `0x00` или `0x7A`, поэтому ложных разделителей не возникает.
Проверено на собранном RU-файле: количество `0x00` в пуле ровно
`число_строк − 1`.

Опасность существует только для **латинских вставок в русском тексте**: буква
`z` допустима (она кодируется как `z` и не ломает пул), но литеральный `U+0000`
в тексте недопустим — `ru_mtfl.py` на него ругается.

## 6. Пересборка при изменении длины текста

1. Разобрать пул в список слотов (строк) в исходном порядке.
2. Для каждого поля каждой записи взять новый текст. Если на один слот
   ссылаются поля с *разным* новым текстом (типично: общий слот-маркер
   `<srw-tag=…>` у 111 статей, а переведена одна), слот сохраняет
   «основной» вариант, а расхождения дописываются новыми слотами в конец пула.
   Неадресуемые слоты (заглушка) остаются на месте.
3. Пересчитать смещения: `off[i+1] = off[i] + len(utf8[i]) + 1`.
   Последняя строка без терминатора (как в оригинале).
4. Пересчитать длины как **число кодовых точек**.
5. Переписать 147 записей `lkke` (остальное в `lkke` не меняется).
6. `jstr.total = 16 + len(pool)`, `jstr.payload = len(pool)`.
7. `kwrb.payload = lkke.total + jstr.total`, `kwrb.total = 16 + payload`.
8. `content_size` в файловом заголовке `= kwrb.total`.
9. Дописать хвост `ENDoMTFL…` без изменений.

Порядок слотов сохраняется, поэтому при пустом переводе результат
**побайтово совпадает** с оригиналом.

## 7. Инструмент `ru_mtfl.py`

```
python _tools/ru_mtfl.py info    <in.dat>
python _tools/ru_mtfl.py extract <in.dat> <out.json>
python _tools/ru_mtfl.py apply   <extracted.json> <ru.json> <translated.json>
python _tools/ru_mtfl.py rebuild <in.dat> <translated.json> <out.dat>
```

`rebuild` берёт структуру из исходного `.dat`, а тексты — из JSON, поэтому JSON
остаётся чисто текстовым и редактируемым вручную.

### Формат JSON

```json
{
 "format": "MTFL/kwrb keyword table",
 "source_sha256": "…",
 "entry_count": 147,
 "articles": [
  {"idx": 0, "id": 3, "flag": 4294967295,
   "term": "Axis Shock",
   "series": "Mobile Suit Gundam: Char's Counterattack",
   "desc": "A phenomenon seen during…",
   "desc2": "",
   "desc2_mode": "same"}
 ]
}
```

`desc2_mode` ∈ `same` | `append` | `full` | `shared` (см. §4).
Менять можно `term`, `series`, `desc`, `desc2` — длина произвольная.
Поля `idx`, `id`, `flag` менять не нужно (`idx` используется для привязки).
Для полного контроля можно задать `desc2_raw` — тогда строка `desc2`
записывается дословно, в обход `desc2_mode`.

`apply` сливает перевод из файла вида
`{"articles":[{"term_en", "term_ru", "series_ru", "text_ru", "text2_ru"}]}`
(`_extracted/keywords_ru.json`) в JSON от `extract`, подставляя `\n` перед
`text2_ru`, как в оригинале.

### Проверка round-trip

```
python _tools/ru_mtfl.py extract <in.dat> tmp.json
python _tools/ru_mtfl.py rebuild <in.dat> tmp.json rt.dat
# rt.dat байт-в-байт равен in.dat
```

| файл | sha256 |
|---|---|
| EN оригинал и round-trip | `569c147adae03ca2189f31537cee94c7e852dfaf28ff5a6554d5602c6180118b` |
| JP оригинал и round-trip | `eee89a0d59a1506b3486a3e9e227b33648dd5b497250572fd0d18c861f1816c6` |

## 8. Сборка CPK

```
python _tools/ru_mtfl.py rebuild "_extracted/MtV_kw_dec/00000000.dat" kw_RU.json MtV_kw_RU.dat
python _tools/srwv_encrypt.py  MtV_kw_RU.dat MtV_kw_RU_enc.dat
python _tools/ru_cpk_patch.py  "CommonData/MtData/EN/MtV_all_keyword_def.cpk" \
                               "_build/MtV_kw_RU.cpk" 0=MtV_kw_RU_enc.dat
```

CPK — ITOC-типа, одна запись (id 0), хранится без сжатия, контент с `0x970`.

## 9. Объём для перевода (EN)

* 147 статей × (термин + сериал + описание [+ доп. текст]);
* 108 301 кодовая точка по всем полям, 346 уникальных строк /
  102 731 кодовая точка без учёта повторов (общие названия сериалов и маркер);
* самая длинная статья — 2 200 символов.
